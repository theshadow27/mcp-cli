## The thing worth remembering

**I stalled my own sprint for seventeen hours.**

The harness killed both my wakers at 03:25Z with exit 144 — the supervisor signalled the
wrapper shells and orphaned the children, which kept running with nowhere to report (#3396).
Fine; I re-armed. But the filter I wrote to suppress replay noise was:

```
select((.ts|fromdateiso8601? // 0)*1000 >= $start)
```

`fromdateiso8601` cannot parse `2026-08-27T03:07:06.779Z` — jq wants whole seconds. The `?`
swallowed the error, `// 0` substituted zero, and `0 >= $start` was false for every event
that has ever existed. The monitor process was healthy for 20.6 hours and emitted nothing.

In that window #3192 opened a green PR that nobody looked at, and its impl session wandered
into an inter-session mail loop and burned $6 → $32. I found out only because the user asked
"what happened to the sprint."

The lesson is not "check your jq." It is that **a killed waker and an armed-but-silent waker
present identically**: no events, no errors, no failing process. The one distinguishing
signal is that the output file is zero bytes after twenty hours, and nothing — not me, not
the harness, not the daemon — was watching for that. Every other liveness trap we have
recorded (halt without a durable artifact, sprint 77's 19-day stall) is the same shape:
silence that looks like patience.

I had also, an hour earlier, written a durable pause note saying "#3192 needs a resume
nudge" — and then correctly updated it to "do not nudge again; it is running." That habit is
the only reason the recovery was five minutes instead of a re-derivation. Keep doing it.

## Two real defects, both caught by review, neither by CI

- **#3036**: six live-reproduced guard bypasses. The guard's verdict and the dispatched
  command's behaviour were different code paths; all 87 new tests called the guard directly
  and none spawned the real CLI. Green tests, broken feature.
- **#3192**: a sole dispatcher on a registered domain accepted events it structurally could
  not resolve, then ran the module with `workItemId: undefined` — worse than the global
  dispatcher it replaced. The existing test never seeded a work item, so it could not tell
  a correct resolution from no resolution at all.

Both are the same failure of test *shape*, not test count: the assertion never crossed the
seam where the bug lives. Worth a rule if we can find a mechanizable form.

## Papercuts carried forward

- Stale `session_id` blocks `phase advance` — impl, repair, qa, across two sprints. And
  clearing the key makes impl **re-spawn** on an issue whose PR is already open and green.
  Order matters: `work_items_update` to the target phase first, *then* advance.
- `phase_state_delete` answers `deleted: false` for a key that never existed instead of
  erroring, which quietly hides a wrong key name.
- QA still writes `review:pass` (#3179 — there is no `review:repaired` state to write).
