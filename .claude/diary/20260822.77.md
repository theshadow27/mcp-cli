Sprint 77 started 2026-08-03, halted at a quota freeze eleven hours later, and was
wound down nineteen days after that. This entry is written at the wind-down, not at
the end — because there wasn't one.

## What worked well

- **The blocked-by edges were all correct.** Every serialization edge in the plan
  predicted a real hot-file collision. #2659 → #935 → #1510 → #1829 shared the
  `envOverrides` block; #1924 → #1939 shared the monitor envelope; #1245 → #1249 shared
  the confluence provider. None of them collided, because none of them ran concurrently.
  The chain was also the failure amplifier: one freeze stalled four issues at once.

- **#2690 paid for itself inside three weeks.** Added to scope mid-sprint after host CPU
  contention — not API quota — turned out to be the throughput bottleneck (12 concurrent
  sessions on a 16-core host drove load to ~19 and produced 112 spurious test failures on
  #2659 alone). The gate-lease is what let *this wind-down's own* `am-i-done` survive: at
  load 16 it queued 192s for a slot and then admitted at 45% CPU, instead of joining a
  SIGTERM storm. Crucially it is admission control, not a killer/reaper — the approach
  that caused the sprint 69-70 collapse and was reverted in #2637.

- **Workers refusing a bad brief caught two orchestrator errors.** #2690's implementer
  declined a stale `cores/4` prescription that would have made contention worse. #1328's
  repairer verified its brief against the tree, found it was missing both 🔴 blockers, and
  refused to let the PR merge on a partial delta. Both times compliance would have shipped
  the defect. This is now the third and fourth data point for the same rule.

- **The introspection cadence guard held.** `scripts/check-introspection-round.ts` exited
  1 and blocked this retro until the sprint-77 round actually ran. That guard exists
  because the sprint-57 round was silently skipped when the cadence was prose-only
  (#2506). A prose rule would have been skipped again here — a 19-day-late wind-down is
  exactly the situation where a tired orchestrator waves a step through.

## What didn't work

- **The quota meter lied and the orchestrator believed it — three times.**
  `_metrics quota_status` reported `fiveHour.utilization: 8` while usage was critical,
  because the upstream quota endpoint was itself 429ing and the daemon served cached
  figures with `available: true` and no staleness marker. The orchestrator told the
  operator "quota is fine" three times while continuing to spawn. The contradicting
  evidence was *right there and under-weighted*: every session showed `[RATE LIMITED]` in
  `mcx claude ls`, and `lastError` held the 429. Filed #2944. Operative rule until fixed:
  **`lastError != null` invalidates the utilization reading — fail safe (freeze), not open
  (spawn)**, and a fleet-wide `[RATE LIMITED]` overrides a low utilization number.

- **The orchestrator stopped, and nothing noticed for 19 days.** This is the finding of
  the sprint. The halting orchestrator did everything right at the freeze: it wrote a
  numbered, correct, act-in-this-order resume plan into the sprint file (commit
  `5a1dc128`), listed what was running and must not be respawned, and listed what must not
  be launched. Then its context ended, taking with it the only thing that knew about the
  14:00 EDT resume trigger.

  **A markdown handoff is read by whoever opens it. Nothing polls it.** There was no
  work-item row, no scheduled tick, no daemon state, no event — nothing anywhere that
  could answer "this sprint is frozen and owes a resume at T". HALTED had no
  representation outside prose, so a correctly-executed pause silently became an
  indefinite stop. Filed #3033.

  The freeze itself was not the mistake. Killing in-flight sessions would have wasted
  already-paid work; letting them drain was right. The mistake was that stopping produced
  no durable artifact.

- **The stranded PR: #2964 sat green for 17 days.** State the entire time: `OPEN`, not
  draft, `MERGEABLE`, `CLEAN`, CI green on all five checks, carrying `review:changes`.
  And — this is the part that stings — the delta adversarial review of repair round 2 had
  **already completed**. The sticky comment (id 5185387000) was updated 2026-08-05T01:02Z
  with a full verdict: 🔴1 fixed, 🔴2 fixed for the path that mattered and descoped to
  #2980 for the path that didn't, all eight 🟡s landed, every MUST-STILL-HOLD verified,
  and a "Scope for the repairer" section listing exactly three small items — one ~3-line
  ENOENT fix and two documentation-honesty edits.

  Nobody read it. The work remaining was under an hour. It waited seventeen days.

  The detectable invariant is embarrassingly cheap: **a PR carrying `review:changes` whose
  head commit is newer than the review that set the label is waiting on nobody.** Either
  ordering of (head commit date, review comment date) is actionable — head newer means
  re-review is owed, review newer means repair is owed. It is one GitHub API comparison.
  Filed #3031.

- **The container PR stayed a draft.** #2923 sat as a draft for 19 days holding the
  sprint's entire bookkeeping trail off `main`. A draft PR is invisible to every gate we
  have: branch protection doesn't apply, auto-merge can't be armed, CI results don't
  matter, no label or review state is expected. It is simultaneously the one artifact
  guaranteed to exist for every sprint and therefore the cheapest possible liveness probe
  — "open draft PR whose head branch matches `sprint-*` with no commits for N days"
  answers "did a sprint fail to wind down?" in a single API call. Filed #3032.

- **THE technical finding of the run phase: tests that cannot express the failure.** Five
  of six adversarial reviews found code that passed a green `am-i-done` and green CI while
  being functionally broken. Every reviewer caught it the same way — by *running* the code
  at production settings — and no test could have caught any of them, because in each case
  the test and the code encode the same assumption.

  | PR | What the test did | What shipped |
  |---|---|---|
  | #1702 | Asserted a rule was dead, per the code's own rationale | Hard-failed a **working** deny rule |
  | #1540 | Real-jq fixture authored from the code's hypothesis | Captured **Sent Items** as the inbox |
  | #1245 | Pinned `retry: { maxRetries: 0 }` — a config **no caller produces** | Adaptation inert |
  | #2690 | Pinned `slots: 1`, never exercising the default `K=2` | Docstring asserted an invariant the code lacked |
  | #1590 | Injected an **exact-advance** virtual clock (`now += ms`) | Timer overshoot unrepresentable |

  Two species, and the second is worse. **Config-pinning** is mechanically detectable —
  flag a spec that only ever exercises an option at an explicit non-default value.
  **Harness-blindness** is not: the test *scaffolding* cannot represent the failure mode at
  all, so it is immune to more tests written on the same harness. A green suite there is
  not weak evidence, it is *no* evidence, and it actively reads as assurance.

  Corollary that changed orchestrator behaviour mid-sprint: **CI green is not evidence
  against a blocker whose failure mode the harness cannot express.** #1590 was green on all
  five checks in both rounds while carrying a reproducible duplicate-write bug.

- **Briefing a repair from a session summary instead of the PR sticky.** On #1328 the
  orchestrator scoped a repair to findings 10-13, silently dropping both 🔴 blockers and
  🟡3-7. The sticky said plainly *"In scope — fix on this PR: blockers 🔴1 and 🔴2, plus
  🟡3-7 and 🟡10-12"*; the orchestrator briefed from the reviewer's **closing session
  message**, which summarised only what its second-opinion agents had *added* — a strict
  subset presented as if it were the finding list.

  Caught only because the repairer verified the brief against the tree. Had it complied,
  #1328 would have merged with a defect that bricks the store on one malformed line plus a
  dedupe key that makes the documented recovery procedure silently double the history. That
  second one is not hypothetical: **during this sprint the branch accidentally migrated the
  live orchestrator log, and recovery was performed by restoring the parked copy — the exact
  path blocker 🔴2 corrupts.** With it merged, that recovery would have doubled 1919 entries
  and bricked the pipeline on the next transition.

- **`mcx claude spawn --resume` silently discards `--allow`.** Cost two rounds during this
  wind-down. A session spawned without an allowlist can only run a read-only subset; resuming
  it *with* `--allow` changes nothing and reports no error, so the only recovery is to throw
  away its context and respawn. A fresh spawn with the same flags works — proven with a
  three-command probe. To the session's credit it refused to route around the control (it
  explicitly declined to use `git commit` as a way to get `bun` to execute via the pre-commit
  hook) and reported the block instead. Filed #3115.

## The wind-down itself, 2026-08-22

Recovering #2964 took four hours and four repair rounds, and the shape of it is the argument
for why the strand was expensive rather than merely embarrassing.

The sticky's remaining scope on day one was *three small items* — one ~3-line ENOENT fix and
two documentation-honesty edits. Round 3 fixed the two prescribed sites and then wrote comments
asserting the invariant held. A fresh adversarial reviewer found the other two sites (`unlinkSync`
×2, `renameSync`) and reproduced the consequence with two real processes: **a transition
committed to the database while the process exited non-zero** — a successful write reported as a
failure, at the exact concurrency premise #1328 exists to fix. Round 4 fixed all four and added
`scripts/rules/staging-path-enoent-tolerant.rule.ts` to hold every staging-path syscall to the
ENOENT branch.

**The rule is the durable half, and the reasoning behind accepting it is the more interesting
artifact.** The repairer could not write a behavioural regression test for the three new sites —
the natural window is one syscall wide, and 6 concurrent processes × 40 rounds against a
deliberately unfixed build produced *zero* failures. It proved the bug with a widened window
instead (40ms injected between `link` and `unlink`: 12/12 pre-fix failures, 0/12 after) and
substituted a rule for the test.

That is exactly the judgement call this sprint's defining finding is about, and it went the
right way — but only because the substitute is falsifiable. The reviewer's reasoning is worth
preserving: *a rule swapped in for a test is only honest if the rule can fail.* The flagged
fixture declares `@expect 3` against the precise round-3 defect shape and
`scripts/rules/fixtures.spec.ts` asserts it. Sprint 77's failure mode was shipping a test that
could not express its failure **while presenting it as if it could**; declaring the limit out
loud and substituting something that covers more is the lesson applied, not violated.

Two things the reviewer did that are worth copying. It **published the negative result against
its own interest** — the 0-failures-in-240-attempts number is what proves the natural window is
undrivable, and someone gaming the review would have buried it. And it **declared the one thing
it had not verified**: it traced the fixture assertion statically but never watched it execute,
said so in the approval, and named the exact command that would close it. QA was briefed to run
that experiment and to deliberately break the rule to confirm the spec fails.

Also of note: #2690's own gate-lease, merged in this sprint, failed open after 242s under a
saturated host and the next run died in a SIGSEGV cascade. The lease is scoped **per repo, not
per host**, and a second project shares the box — so `slots=1` can be perfectly satisfied while
the machine is at load 40. A healthy lease is not evidence of an idle host; `uptime` is. Filed
#3136.

## Patterns established

- **A halt must produce a durable artifact, not prose.** Any orchestrator state that expects
  a future action — frozen-until, blocked-on, awaiting-review — has to live somewhere a
  reconciler can read after the writing context dies. This is the sprint-operator thesis
  (#1942/#2577) arriving as a bill rather than an aspiration: a stateless reconciler that
  re-derives "what should be happening now" from persisted state is precisely the thing that
  survives its orchestrator dying.

- **Label state and commit timeline should be cross-checked, not read separately.** Every
  stranded artifact this sprint was derivable from GitHub metadata alone. Nothing was looking.

- **Impl brief bar: demonstrate behaviour at the DEFAULT configuration with observed numbers,
  not asserted intent.** Improvised in this sprint's repair briefs and it worked — #1245 came
  back with `expect(observedLimits).toEqual([250,125,62,31,25])` and a spec comment reading
  *"Do not add `maxRetries: 0` to these tests. That configuration has no caller."*

- **Review brief gets an explicit checklist item:** for every test that passes a config
  override, is the default also covered — and *can this harness represent the failure at all?*

- **The PR sticky comment is the authoritative finding list.** A session's closing message is
  a summary written for the orchestrator, not a spec. Always read the sticky before writing a
  repair brief, enumerate findings by identifier (🔴1, 🔴2, 🟡3-7) *and state the count*, and
  tell every repairer to verify the brief against the review and flag a mismatch rather than
  silently scoping to what it was told.

- **Rejected: a dedicated adversarial-test-writer phase.** It would duplicate the review
  phase, which caught 5/5 of these, at ~16 extra sessions per sprint — and a test adversary
  working from the issue text can encode the same wrong assumption an implementer does.
  Revisit only if the impl-brief change ships and the class still appears at this rate.
