## What the lane model proved

Turnover beats headcount. Fresh subagents per phase, worktree carrying the
branch, ledger carrying the state: the orchestrator compacted once mid-sprint
and reconstructed everything from `work_items` + labels + the plan file.
Spend stayed sane (7-day utilization read 31% when quota finally became
measurable). Nobody idled hot; finished agents ceased to exist.

Losses in the model, all recoverable: **completion notifications were lost at
least three times** (finishers committed, then waited forever to be woken;
fixed each time by a status-check nudge against ground truth — `[ahead 1]`
with no live gate process is the tell). The harness wake path needs to be
treated as at-most-once delivery: the orchestrator owns periodic ground-truth
reconciliation, not the workers.

## The wedge, caught live

Two live captures of the #2973/#3250 am-i-done wedge in one night — first
with a zombie `ps` child, second (independent reproduction, same QA run) with
a zombie `git` child, which widened the suspect set from ps/lsof shell-outs
to any synchronous-spawn site. Discriminator that held both times: CPU-time
tracking wall-time ~1:1 with an unreaped zombie proves a blocked event loop —
a busy worker that later finishes is NOT the signature. A QA agent initially
rationalized wedge #1 as "load contention, making progress"; /proc forensics
(zombie child 29 min unreaped, ~28 CPU-minutes ≈ 5× the suite's total work,
half the cores idle) disproved it. The corrected method is now in the QA
briefs.

Bounded the failure mode the same night: #3261 shipped a strict wall-clock
deadline (default 300s, `AM_I_DONE_TIMEOUT_MS`, CI 600s from measured
178–242s baselines) with process-group tree-kill scoped to own children —
no ps parsing, no reapers, per the sprint-70 rule. Its own deadline armed
during the pre-push gate that validated it. QA's guard-mutation check found
the SIGKILL-escalation branch untested (#3271) — the mutation discipline
keeps earning its keep (it also caught nothing else all sprint because the
implementations were genuinely covered).

## The human-gate failure

Lane 2 sat parked "pending operator quota confirmation" — an improvised
mid-sprint human gate. Operator ruling, now doctrine
(`feedback_no_human_gates_mid_sprint.md`, and to be written into plan.md by
this retro's meta pass): **a sprint runs unattended end-to-end.** Approvals
live in planning; surprises spike to next planning; catastrophes spike the
sprint. The aggravator: the plan's own quota check (`quota_status` before
each lane) was unexecutable because quota monitoring was dead on Linux —
which was #3223, sitting unstarted in the same sprint. The tool to make the
decision was the backlog item the decision was blocking on.

## Model-tier drift, caught by the operator

The operator's original complaint (sprint 78/79 boundary) was **fable spawned
for implementation and QA, sessions left open for 100ks of tokens**. By
mid-sprint 79 that had mutated — via a quota-lean plan table ("implementers
default sonnet") laundered through memory files — into sonnet implementing
diagnostic work. Operator: "unsanctioned, untracked, machine-specific
memories that now want sonnet to implement by default? That's problematic."
Corrections shipped: memory rewritten to the actual rule (opus implements;
sonnet review + mechanical only; fable never for dev/QA; nothing idles hot),
lanes.md rule 9 closed the "(or per the plan table)" loophole, and — the
structural fix — **memories now get committed in-repo** (PR #3270): "That
keeps the memories honest. Without that, they tend to get carried away."
Second-order lesson from the same exchange: no revision narration in
always-loaded documents — state the rule, keep the story in the diary.
